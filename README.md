# hack-2cc01208-anomaly-detected

Команда **Anomaly Detected** · HackAlem AI · Track 06 Creative Industries · кейс «Smart contractor matching» (Firebird).

Пользователь вводит параметры заказа (город, дата, тип события, категория, бюджет, часы, язык)
и получает до 3 подрядчиков с конкретным объяснением, почему каждый подходит.

## Структура

```
backend/   — API подбора (Python)
frontend/  — index.html + app.js + style.css, без сборки
data/      — hackathon-dataset-anonymized.jsonl
docs/      — api.md (контракт между фронтом и бэком)
```

## Как это работает

Три шага, каждый со своей ролью и своей проверяемостью:

```
запрос → фильтрация (детерминированно) → ранжирование выживших → объяснение по карточке → ответ
         без модели, чистый код             embeddings + cosine,     LLM, temperature=0,
                                             id как tie-break         факты только реальные
```

1. **Фильтрация** (`backend/app/filters.py`) — обычный код, без модели. Город, категория, формат
   события, бюджет, занятость на дату, язык, длительность — всё проверяется явно. Для каждого
   отфильтрованного кандидата фиксируется причина (`busy_on_date`, `over_budget`, `wrong_format`,
   `wrong_language`, `too_few_hours`) — это и есть блок `excluded` в ответе API, который отдаётся
   всегда, а не только при пустом результате.

2. **Ранжирование** (`backend/app/ranking.py`) — среди тех, кто прошёл фильтры, ранжируем по
   косинусной близости эмбеддинга запроса и эмбеддинга свободного текста `description` подрядчика
   (тот же паттерн embed+cosine, что уже использовался в `agent-kit/python/agent_kit/rag.py`,
   применённый не к чанкам документа, а к профилям каталога). Сортировка — `(relevance desc, id asc)`:
   `id` как tie-break — это и обеспечивает детерминизм даже при равных оценках релевантности.
   Если вызов эмбеддингов не удался (нет ключа, нет квоты, нет сети) — детерминированный fallback
   по близости цены к бюджету, без модели вообще.

3. **Объяснение** (`backend/app/explain.py`) — один вызов LLM на карточку (`temperature=0`),
   с промптом, который получает только реальные поля подрядчика и явно запрещает придумывать
   факты или использовать общие фразы вроде «отличный выбор». При недоступности LLM — шаблон,
   собранный из тех же реальных полей: демо не должно зависеть от того, есть ли в моменте кредиты
   на OpenAI-ключе.

Ни на каком этапе модель не дообучается — задача прямо это исключает («Дообучение модели на
66 записях... это пересказ датасета. Готовые эмбеддинги и LLM через API — пожалуйста»).

## API

Полный контракт — в `docs/api.md`. Кратко:

- `POST /api/match` — тело: `city, date, event_type, category, budget_kzt`, опционально `hours, language`.
  Ответ: `status` (`found | no_category | none_fit`), `message`, `cards[]`, `excluded{}` (всегда).
- `GET /api/options` — списки `cities, categories, event_formats, languages` для выпадающих списков на фронте.
- `GET /health` — количество загруженных профилей, для быстрой проверки, что бэкенд поднялся и данные прочитались.

## Данные

`data/hackathon-dataset-anonymized.jsonl` — 66 профилей подрядчиков (партнёрский анонимизированный
датасет, JSON-объект на строку). Реальное распределение по категориям в файле: Ведущий — 15,
Фотограф — 12, Банкетный зал — 8, ещё несколько категорий по 4-7, и семь редких категорий
(Флорист, Декоратор, Подарки и сувениры, Ведущий церемонии, Фото и видеобудки, Отель,
Инструменталист) — по 3 профиля каждая, что ровно совпадает с числами из условия задачи.

Поле `synthetic` сохраняется на всём пути до карточки в ответе API — если когда-нибудь понадобится
дополнить датасет своими профилями для покрытия демо-сценария, `load_contractors()` в
`backend/app/data_loader.py` принимает список `extra_synthetic`, и такие профили останутся
явно отличимыми от настоящих, а не подмешаются молча.

## Install & run

### Backend

```bash
cd backend
pip install -r requirements.txt
cp .env.example .env        # вписать свой OPENAI_API_KEY
python -m uvicorn app.server:app --port 8000
```

Без `OPENAI_API_KEY` (или при исчерпанной квоте) сервис всё равно работает — ранжирование и
объяснения переключаются на детерминированный fallback без модели, статус ответа не меняется.

Проверка, что всё поднялось:

```bash
curl http://localhost:8000/health
```

### Frontend

Без сборки — просто статические файлы, но открывать напрямую как `file://` не стоит (некоторые
браузерные расширения и CORS-политики режут такие запросы к `localhost`). Проще всего поднять
локальный сервер:

```bash
cd frontend
python -m http.server 5500
```

и открыть `http://localhost:5500`. Бэкенд должен быть уже запущен на `:8000` — CORS настроен
как `allow_origins=["*"]`, так что порт фронта (5500 или любой другой) значения не имеет.

## Тесты

```bash
cd backend
pytest tests/ -v
```

12 тестов, реально бьют в живой OpenAI API (не моки) и проверяют:

- все три статуса (`found` / `no_category` / `none_fit`) действительно достижимы на реальных данных;
- `excluded` присутствует и корректно посчитан в любом статусе, включая `found`;
- занятость на дату, язык, длительность (`hours`) реально исключают неподходящих кандидатов,
  и `max_hours = null` (работа не привязана к присутствию — флорист, декоратор) никогда не
  исключается фильтром по длительности;
- категория-площадка (например, «Банкетный зал») проходит через тот же самый пайплайн без
  специального кейса — именно так, как это описано в условии задачи;
- один и тот же запрос дважды подряд даёт одинаковый порядок карточек;
- два разных объяснения в одном ответе не совпадают даже после подстановки `<NAME>` вместо имени
  (проверка на «карточки не должны путаться друг с другом»).

Также пройдена ручная проверка воспроизводимости: `pip install -r requirements.txt` в чистом
venv + `pytest` — 12/12 зелёных без какого-либо ручного вмешательства.

## Демо-сценарии

```bash
cd backend
python demo_queries.py
```

Прогоняет 5 сценариев, три из которых явно требуются условием задачи:

1. Плотная категория на осеннюю дату (Фотограф, Алматы) — где ранжирование реально решает.
2. Редкая категория (Флорист, 3 профиля) — граница между «нашли» и «нашли мало».
3. Запрос без результата (нереалистичный бюджет в пиковую дату) — проверка честного `none_fit`.
4. Категория-площадка («Банкетный зал») — тот же пайплайн, что и для любого другого подрядчика.
5. Комбинация фильтров по языку и длительности — оба необязательных поля работают вместе.

## Определённость и устойчивость

- **Детерминизм** — `id` как вторичный ключ сортировки при равном `relevance`, `temperature=0`
  на генерации объяснений. Один и тот же запрос всегда возвращает карточки в одном порядке.
- **Разные даты — разный результат** — занятость считается по `busy_dates` каждого подрядчика,
  так что смена даты меняет и множество кандидатов, и (через `excluded.busy_on_date`) видимую
  причину, почему кто-то не попал в выдачу.
- **Без модели — тоже работает** — ранжирование и объяснения имеют детерминированные fallback-пути
  без единого вызова к внешнему API. Основной сценарий не ломается из-за отсутствующего ключа,
  исчерпанной квоты или сетевой недоступности во время демо на площадке.
- **Скорость** — параллельные вызовы объяснений на карточку (а не последовательные) держат полный
  ответ на 3 карточки в районе 3-4 секунд «в тепле», с запасом от требуемых 10 секунд.

## Известные ограничения

- Без валидного `OPENAI_API_KEY` с доступной квотой ранжирование и объяснения работают в
  fallback-режиме — статусы и структура ответа не меняются, но текст объяснений получается более
  механическим (см. поле `explanation_source` в каждой карточке: `"llm"` или `"template"`).
- Нет бронирования, заявок или уведомлений подрядчику — только рекомендация, согласно условию задачи.
- Нет сложного UI сверх формы и карточек результата — согласно прямому указанию в условии
  («если выбирать между интерфейсом и качеством объяснений — берите объяснения»).
